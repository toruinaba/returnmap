# 仕様書から実装する

モデルのファミリの仕様書を書き、それをもとに実装を依頼し、結果を確認する手順を示す。実装する者は、人でも LLM でもよい。段階ごとの実装の内容は [新しいモデルを足す](adding-a-model.md) にあり、このページは仕様書と受け渡しを扱う。

仕様書は、ファミリの `README.md` である。雛形と指示文は [`examples/model_family/templates/`](https://github.com/toruinaba/returnmap/tree/main/examples/model_family/templates) にあり、完成した例は同じ雛形の [`src/mymodels/voce/README.md`](https://github.com/toruinaba/returnmap/blob/main/examples/model_family/src/mymodels/voce/README.md) である。

## 1. 手順

| 段階 | 行う者 | 内容 | 成果物 |
|---|---|---|---|
| 1 | 仕様を決める者 | 仕様書を書く (2 節、3 節) | 空欄を含む `README.md` |
| 2 | 実装する者 | モデル、手書きの解法、UMAT、テストを作り、検査に通す。仕様書の空欄を書く (4 節) | コードと、空欄の埋まった `README.md` |
| 3 | 仕様を決めた者 | 結果を確認する (5 節) | — |

| 項目 | 内容 |
|---|---|
| 実装の分担 | 段階 A (自動微分で解くモデル)、B (手書きの解法)、C (UMAT) ごとに分けられる。検査は、モデルが宣言しているものから決まり、誰が書いたかに依らない |
| すでに実装した段階 | 指示文の「進め方」と「作るもの」から外し、そのファイルを「場所」に挙げる |
| 解法の決め方 | 仕様書の「手書きの解法」を書いて渡すか、空欄で渡して実装する者に任せる |

## 2. 仕様書

仕様書は、完成時の文書に空欄がある状態として書く。

| 項目 | 内容 |
|---|---|
| 書いてある節 | 実装はその節に従う。内容を変える場合は、実装より先に仕様書を変える |
| 空欄 | `(未記入)` と書く。実装した者が、実装の結果を書く |
| 記述 | 完成時にそのまま残る記述のみを書く。実装の前は要求として、後は確かめられた事実として読める形にする |
| 書かないもの | 作業の指示、誰が決めたかの印、実装の経緯。これらは指示文と報告に書く |

雛形は次のとおりである。`〈〉` を埋めて用いる。

```{literalinclude} ../../examples/model_family/templates/family-README.md
:language: markdown
```

| 節 | 空欄にできるか | 空欄にする場合 |
|---|---|---|
| クラスの表、「式」、「状態変数」、「パラメータ」、「性質」 | できない | — |
| 「手書きの解法」 | できる | 小見出し (縮約、反復、応力と接線) を残し、それぞれを `(未記入)` にする |
| 「近似」 | できない | 解法が空欄でも、近似を許すかどうかは書く |
| 「UMAT」 | 一部できる | 解法から決まる行 (リンクするライブラリ、接線の対称性) を `(未記入)` にする |
| 「検証」の「対象」 | できない | — |
| 「検証」の「報告」「範囲」 | 常に空欄で渡す | — |

到達点に無い節 (自動微分のみのファミリの「手書きの解法」「UMAT」) は、節ごと置かない。

## 3. 書き方の規則

### 式

| 項目 | 規則 |
|---|---|
| 出典 | 出典と、出典との差を書く。差が無い場合は「無い」と書く |
| 量の種別 | 記号ごとに、応力系・ひずみ系・スカラーの別を書く。成分の順序を書く |
| 工学せん断ひずみ | $2\varepsilon_{12}$ と書く。$\gamma_{12}$ は用いない |
| 記号 | 大文字と小文字のみが異なる記号を用いない (Fortran では同じ名前になる)。ほかの参照モデルのパラメータ名と同じ記号を別の意味で用いる場合は、その旨を書く |
| 離散化した式 | 全部を書く。各量を評価する時点 ($n$ か $n+1$) を添字で示す |
| 弾性ステップ | 条件と、そのときの各状態変数の値を書く |
| 微分できない点 | 0 になりうるノルム、括弧 $\langle\cdot\rangle$、べき乗について、その点での扱いを書く |
| 数値上の扱い | 実装が従う扱い (正則化の値、下限の値) を書く。どの経路がどの条件で収束するかという観察は、「検証」の「範囲」に書く |

### 状態変数とパラメータ

| 項目 | 規則 |
|---|---|
| 状態変数 | 種別、形、初期値を書く。`stress` を宣言しない場合は、種別を「—」にする |
| 次元による違い | 次元によって持ち方が変わる状態変数は、その持ち方を書く |
| パラメータ | 単位、目安の値、範囲を書く。宣言の順序は表の順序とし、`PROPS` の順序と一致させる |
| 範囲 | `check_range` が検査する端になる。1 つだけを端に置くと意味を失う組がある場合は、その制約を書く (`verification.py` の `variants(model)` に対応する) |

### 性質

| 項目 | 規則 |
|---|---|
| 内容 | 実装を見ずに書ける値のみを書く。実装より先に書く |
| 行の構成 | 性質ごとに、対象、載荷、性質、許容値を書く |
| 載荷 | 成分、折り返し点、区間ごとのステップ数で書く。区間は等分割で、始点を含まない |
| 対象のステップ | 「塑性ステップの全部で」「全ステップで」「最終ステップで」のいずれかを書く |
| 誤差を測る範囲 | 性質が指すステップの値を並べた配列の全体。これと異なる場合は、その行に書く |
| 成り立つ条件 | 式が成り立つ載荷の向きや符号を書く |
| ほかのモデルとの比較 | 相手のクラス、パラメータ、経路を書く |
| 制御の種類 | ひずみ制御か、混合制御かを書く。混合制御では、ひずみを与える成分と、応力を 0 にする成分を全部書く。`standard_histories` の `"uniaxial"` は、第 1 成分のひずみだけを与えるひずみ制御であり、単軸応力ではない |
| 入れる種類 | 降伏条件、塑性ひずみの大きさ、純せん断、体積応答、飽和値、退化 (既存のモデルとの一致)、次元の間の一致、発展則の離散形 |
| 発展則の離散形 | 内部変数ごとに、多軸の載荷で、テンソルのまま確かめる行を入れる。飽和値と直成分の和のみでは、発展則の係数、評価する時点、法線の種別の誤りを検出できない |
| パラメータ | 目安の値で働かない機構がある場合は、それが働く値でも確かめる |

### 手書きの解法

| 項目 | 規則 |
|---|---|
| 構成 | 「縮約」「反復」「応力と接線」に分ける |
| 内容 | 別の者がこの節のみから実装し直せる内容にする。反復に用いる微分も書く |
| 反復 | 表にする: 方法、未知数、初期値、更新、収束の判定、反復の上限、収束後の確認 |
| 反復の上限 | 更新の回数で書く。初期値で収束を判定するかどうかも書く |
| 収束後の確認 | 非収束として扱う条件を書く。解法の上で到達しない条件は、その旨を書く |
| 実測値 | 1 ステップの更新の回数を書く |
| 接線 | 対称かどうかを書く |

### 近似と UMAT

| 項目 | 規則 |
|---|---|
| 近似 | 無い場合は「無い」と書く。ある場合は、対象、条件、許容値、理由を表にする。表に無い近似は、実装で宣言しない |
| 検査の設定 | 検査の許容値と載荷履歴が既定と異なる場合は、「近似」に書く |
| 中核の引数 | 入力と出力の並びを書く |
| `PROPS`、`STATEV` | 並びを番号で書く |
| 非収束時の出力 | 中核と、Python の手書きの経路の両方について書く |
| 入口 | 非収束時と収束時の挙動を書く。引数の宣言は [UMAT を確かめる](model-umat.md) の 4 節に従う |
| 解法から決まる内容 | 表に値を書かず、「手書きの解法と同じ」と書く |

### 検証

| 項目 | 規則 |
|---|---|
| 対象 | 検査するクラスとパラメータを書く。パラメータが複数ある場合、UMAT の比較もその全部で行う |
| 報告 | UMAT をビルドした環境で `returnmap check --family <パッケージ> --require-built --range` が表示したものを、`none` のブロックに書く。性質のテストの結果を書く |
| 範囲 | テストで確かめていること、テストに無くコマンドや手で確かめたこと、確かめていないことを分けて書く |

### 複数の次元

既存のファミリに次元 (平面応力など) を足す場合は、仕様書を次のとおりに書き足す。既存の次元の節は変更しない。

| 節 | 書き足す内容 |
|---|---|
| クラスの表 | 新しい次元のクラスの行 |
| 記号と量の種別 | 新しい次元での成分の順序 |
| 状態変数 | 新しい次元での持ち方を表にする。returnmap の次元の名前を書く (平面応力には、偏差の 33 成分を復元する `PLANE_STRESS` と、面内の成分をそのまま持つ `PLANE_STRESS_P` がある) |
| 性質 | 新しい次元のクラスの表を足す。検証済みの次元との一致の行を入れる |
| 手書きの解法 | 次元ごとに節を並べる: 「手書きの解法 (3D)」「手書きの解法 (平面応力)」 |
| UMAT | 次元ごとに節を並べる: 「UMAT (3D)」「UMAT (平面応力)」。`STATEV` の並びと `NTENS` を書く |
| 検証 | 「対象」に行を足す。「報告」と「範囲」は、実装した者がファミリの全体について書き直す |

| 項目 | 内容 |
|---|---|
| 検証済みの次元との一致 | 平面応力の場合、同じ面内のひずみを 3D のクラスに混合制御 (面外の応力は 0) で与えた結果と、応力・状態変数が一致する。式を変えたモデルの大半は、この行で検出される |
| 検出できないもの | 既存の次元と新しい次元が同じ誤りを持つ場合 |
| 既存の次元のコード | 変更しない。共通の部分を関数に切り出すこともしない。既存の次元の検証済みの状態を保つためである |

## 4. 指示文

指示文は、実装する者に渡す依頼である。手順、合格の条件、規則、報告の項目を書く。

```{literalinclude} ../../examples/model_family/templates/brief.md
:language: markdown
```

| 項目 | 内容 |
|---|---|
| モデル固有の内容 | 指示文には書かない。式、注意点、解法の方針は、仕様書に書く |
| 空欄の無い仕様書 | 「仕様書の空欄」の表から、「手書きの解法」の行を外す |
| 報告 | 事実と結果を求める |
| コンテナ | `make docker-check` は、雛形の `Makefile` と `Dockerfile` が提供する。gfortran のある機械では、同じ内容を直接実行できる |
| 既存のファミリに次元を足す場合 | 「場所」に完成済みのクラス、UMAT、テストを挙げる。「規則」に、変更しないもの (既存のクラス、既存の UMAT、仕様書の既存の節) を書く。「進め方」の段階 A は、次元を固定しただけのクラスを足して `check_model` を通す段階にする |

## 5. 確認

| 確認するもの | 方法 |
|---|---|
| 仕様書の書いてある節 | 実装の前後で `README.md` の差分を取る。消えた行が `(未記入)` のみであること |
| 検査の合否 | `make docker-check` が終了コード 0 で終わること。仕様書の「報告」が、その出力と一致すること |
| パラメータの範囲と乱数の載荷 | `returnmap check --family <パッケージ> --require-built --range`。不合格の組は、原因と合わせて「範囲」に書かれていること |
| 検査の設定 | `verification.py`、`tests/test_verification.py`、モデルの `@hand_block` と `@hand_tangent` の差分。仕様書の「近似」に無い近似、許容値の変更、載荷履歴の差し替えが無いこと |
| 性質のテスト | 期待値がテストの中で式から計算されており、モデルのメソッドから取られていないこと |
| 自動微分で解くモデル | `yield_function` と発展則を、仕様書の「式」と読み比べる。共通の検査は、同じモデルの 2 つの導出を比較するものであり、式の読み違いを検出しない。検出するのは性質のテストのみである |
| 実装で決めた事項 | 報告の一覧を 1 件ずつ、仕様書の該当する節に書き込むか、却下する |
| 確かめていない項目 | 仕様書の「範囲」の該当する行を、受け入れるか、追加の確認を依頼する |
