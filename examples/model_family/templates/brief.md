# 依頼

仕様書を 1 つ渡すので、構成則モデルのファミリを実装し、検査に通してください。作るのは〈Python のモデル、手書きの解法、Fortran の UMAT〉です。〈仕様書の「手書きの解法」の節は空欄で、解法を決めて書くこともこの作業に含みます。〉

## 場所

プロジェクトは `〈プロジェクトの絶対パス〉`(以下 `$T`)です。

- 仕様書: `$T/src/〈パッケージ〉/〈ファミリ〉/README.md`
- `$T/src/〈パッケージ〉/〈既存のファミリ〉/` は、完成済みの別のファミリです。ファイルの構成と書き方の例として読んで構いません。変更はしないでください。
- returnmap は `$T/.venv` にインストール済みです。
- 作業用のファイルは `$T/.scratch/` に置き、最後に削除してください。

コマンドは毎回 `cd 〈プロジェクトの絶対パス〉 && ...` の形で実行してください。

## 使ってよい情報

1. 仕様書。
2. インストールされた returnmap のパッケージ。API の契約は docstring にあります。参照モデル(`returnmap/models/` 以下)も読んで構いません。
3. `$T/src/〈パッケージ〉/〈既存のファミリ〉/`。

## 作るもの

`$T/src/〈パッケージ〉/〈ファミリ〉/` 以下に作ります。

| ファイル | 内容 |
|---|---|
| `model.py` | 仕様書の冒頭の表にあるクラス |
| `verification.py` | 検査にかけるモデル(仕様書の「検証」の「対象」)と UMAT の宣言。仕様書の「近似」に載荷履歴の指定があれば、その宣言 |
| `fortran/〈名前〉.f90` | UMAT。中核のサブルーチンと、ABAQUS の入口 `umat` |
| `tests/test_verification.py` | 共通の検査(`check_model`)。UMAT の比較は、「対象」のパラメータの全部で行う |
| `tests/test_properties.py` | 仕様書の「性質」を、1 つずつテストにしたもの。期待値はテストの中で式から書き、モデルのメソッドから取らない |
| `README.md` の空欄の節 | 下の「仕様書の空欄」 |

コードのコメントと docstring は英語で書きます。

## 仕様書の空欄

仕様書の中で `(未記入)` となっている箇所を書きます。文章は日本語で、技術文書の文体で書きます。

| 節 | 書く内容 |
|---|---|
| 「手書きの解法」の「縮約」「反復」「応力と接線」 | 実装した解法。別の人がその節だけから実装し直せる内容にする。反復は表にする(方法、未知数、初期値、更新、収束の判定、反復の上限(更新の回数)、収束後の確認)。反復回数の実測値と、接線が対称かどうかも書く。解法の方針は自由だが、UMAT はその移植なので、Fortran に移せる形にする |
| 「UMAT」の表の `(未記入)` の行 | 実装した解法から決まる内容 |
| 「検証」の「報告」 | コンテナの中で `returnmap check --family 〈パッケージ〉 --require-built --range` が表示したものと、性質のテストの結果 |
| 「検証」の「範囲」 | テストで確かめていること、テストに無くコマンドや手で確かめたこと、確かめていないこと |

## 進め方

段に分け、各段の合格を確かめてから次に進みます。

| 段 | 内容 | 合格の条件 |
|---|---|---|
| A | 自動微分で解くクラス | `check_model` が通る。この段で確かめられる性質のテストが通る |
| B | 手書きの解法と接線 | `check_model` の手書きに関する行がすべて `passed`。性質のテストが全部通る |
| C | UMAT | コンテナの中で、`check_model` の `UMAT` と `UMAT entry` の行が `passed` |

| コマンド(`cd $T &&` に続けて) | 内容 |
|---|---|
| `uv run pytest` | この機械でのテスト。gfortran が無ければ、UMAT のテストは skip される |
| `uv run returnmap check --family 〈パッケージ〉` | この機械での、全モデルの検査の報告 |
| `make docker-check` | コンテナの中で、宣言された UMAT をすべてビルドし、全テストを実行し、全モデルの検査の報告を出す。未ビルドの UMAT は不合格になる |
| `make docker-run CMD="returnmap check --family 〈パッケージ〉 --require-built --range"` | コンテナの中で、パラメータの範囲の端と乱数の載荷履歴でも検査する |

完了の条件は、次の 2 つです。

- `make docker-check` が終了コード 0 で終わる(テストは失敗 0、skip 0)。
- `--range` を付けた検査で、載荷の組(`loading`)がすべて合格する。パラメータの組(`parameters`)に不合格がある場合は、その組と原因を報告する(パラメータの範囲を狭めるかどうかは、仕様書の側で決める)。

## 規則

- **仕様書に書いてある節に従う。** 書いてある内容が誤っている、または従えない場合は、仕様書を変えずに作業を止めて報告してください。README で編集してよいのは、`(未記入)` となっている箇所だけです。
- **手書きの経路の中で自動微分を使わない。**
- **検査を緩めない。** 検査の許容値を既定より緩めない。載荷履歴は、仕様書の「近似」に書いてあるもの以外に差し替えない。仕様書の「近似」に無い近似を宣言しない。性質のテストの許容値は仕様書の値を使う。
- **通らない検査は、実装を直して通す。** 直せない場合は、通らないまま止めて報告してください。
- git の操作(commit など)はしないでください。
- `$T` の外に書き込まないでください。既存のファミリと、プロジェクトの設定ファイルは変更しないでください。

## 報告

最後に、次の項目を簡潔に報告してください。事実と結果だけで足ります。

1. 段ごとの結果(合格 / 不合格)。最終の `make docker-check` の末尾の出力と、`--range` を付けた検査の出力。
2. 実装した手書きの解法の要約: 未知数の数、反復の方法、1 ステップの反復回数の実測値、接線が対称かどうか。
3. 仕様書に書かれておらず、実装で決めた事項の一覧(項目と、決めた内容)。
4. 仕様書の記述のうち、曖昧だった箇所と、誤りと考えた箇所の一覧。
5. 失敗した検査とテストの一覧(段ごと): どの検査がどう落ちたか、原因、直した内容。
6. 式を 1 か所ずつ変えたモデル(発展則の係数、評価する時点、法線の種別など)に、性質のテストを適用した結果: 検出された変更と、検出されなかった変更。
7. テストにしていない確認の一覧(確かめた内容と回数)。
8. 読んだファイルの一覧。
